# Batch 3: toolchain

Spec version under test: **2.0** (the toolchain section of the Specification page). Levels:
see [runtime-static-lifecycle.md](runtime-static-lifecycle.md#levels).
Probed = the C++ CPU toolchain (`oaax-cpu-toolchain:2.0.0`, reference implementation), run by hand with Docker.

`oaax-conformance toolchain IMAGE [--onnx FILE] [--runtime LIB] [--docker-arg ARG]...`

## What the tests need

- **Docker** on the machine running the suite (a toolchain is a Docker image).
- **A valid ONNX model** this toolchain can convert (`--onnx FILE`; default: a small convolution model shipped with the suite).
  The invalid inputs (empty, garbage, truncated, missing, directory, hostile archive) are generated by the suite.
- `--docker-arg ARG` adds an argument to every `docker run` (for example `--gpus all` for a toolchain that needs the device). Repeatable.
- The end-to-end tests (`E2E-*`) also need `--runtime LIB` (and its `--init-config`): without it they are `BLOCKED`.

Every conversion runs as `docker run --rm --user <uid>:<gid> -v <in>:/input -v <out>:/output IMAGE /input/<file> /output/<dir>`
in temporary directories; unless a test says otherwise the user is the invoking user. Directories owned by another uid are never created
(tests that run as an arbitrary uid write into the existing output directory), so nothing needs root to clean up. Temporary directories are
removed at the end; any that cannot be are listed in the report.

## `TC`: what a failed conversion does

Each case runs the conversion on a bad input into a fresh, writable output directory and expects a non-zero exit code.

| ID | Check | Pass when | Level | Source | Probed | Status |
| -- | ----- | --------- | ----- | ------ | ------ | ------ |
| TC-30 | Empty file | a 0-byte `.onnx` exits non-zero | MUST | spec 3.2: "File Format Validation: Verify ONNX model integrity"; 6.1: "Non-zero: otherwise" | **FAIL**: exit 0, converts an empty model | approved |
| TC-31 | Not an ONNX file | text in a `.onnx` file exits non-zero | MUST | same | pass (exit 1) | approved |
| TC-32 | Truncated ONNX | the first 30% of a valid model exits non-zero | MUST | same | pass (exit 1) | approved |
| TC-33 | Missing input | a path that does not exist exits non-zero | MUST | same | pass (exit 2) | approved |
| TC-34 | Input is a directory | a directory instead of a file exits non-zero | SHOULD | spec 3.1: the input is "an ONNX model file" or an archive | pass (exit 2) | approved |
| TC-35 | Failure log | after TC-31, TC-32 and TC-33 (the output directory is writable) a `conversion-log.json` / `logs.json` with valid JSON exists | MUST | spec 6.2: "For all failure cases, toolchains must: Generate Logs: Produce conversion-log.json with error details" | **FAIL**: none for garbage, truncated or missing input | approved |
| TC-36 | No model after a failure | the output directory holds no model file (only the log) after TC-30 to TC-33 | SHOULD | derived: a host takes "the model" from the output directory; spec 5.1 ties the model file to success | pass for TC-31/32/33; TC-30 "succeeds" | approved |
| TC-37 | Failure is explained | the console output of a failed conversion is not empty | SHOULD | spec 4: "Error Reporting: Human-readable error messages with actionable guidance" | pass | approved |
| TC-38 | Unwritable output | an output path that cannot be created (read-only mount) exits non-zero | MUST | spec 6.1 as above | pass | approved |
| TC-39 | Hostile archive | a `.zip` whose member path is `../../escape.txt` leaves nothing outside the input and output directories (a toolchain that does not take archives passes by rejecting it) | SHOULD | spec 9.3: "Input Sanitization: Validate all inputs to prevent security vulnerabilities" | pass (archives are rejected) | approved |

## Deliberately not tested in 2.0

- Archive input (`.zip`, `.tar.gz`): optional in the spec, and its layout is not defined (what must be inside, where the model is). Only the hostile archive is tested (TC-39).
- Conversion log content: the 2.0 text only says "JSON-formatted"; the schema is a 2.1 topic.
- Exit codes other than 0 / non-zero: the text defines no others.
- Operator coverage and model size limits: vendor-specific; a vendor's unsupported model fails TC-01 with its own `--onnx`.
- Accuracy beyond E2E-04, performance, determinism of the output file.
